# Bench and Active order live in dedicated records, not a field on Player

`Player` already carries a `sortOrder` used to order the roster list in Settings. The Bench queue order (who's Next Up) and the Active order (who subs out next) are each tracked separately in their own singleton-per-context, role-scoped record — two instances of the shared `OrderManager` SwiftData model, distinguished by `OrderManager.role` (`.bench` / `.active`), each with its own `playerOrder: [UUID]` — rather than as additional fields on `Player`.

A single `sortOrder` field can't represent two independent orderings that both need to survive a player moving between Active / Benched / Temporarily Out. `TimerView` re-syncs both role-scoped managers against current player statuses on every appear (`syncOrderManager(role:status:)`) to add players missing from the order and drop ones that changed status — logic that only makes sense because the order lives outside `Player` itself.

Within `OrderManager`, the two records are distinguished by the `role` field's value, not by two subclasses (e.g. a shared base class with `BenchManager`/`ActiveManager` inheriting its CRUD). We considered the class-hierarchy approach and rejected it: `OrderManager` used to be exactly that — `BenchManager` and `ActiveManager`, two separate model types with identical logic apart from doc comments — and it produced matching pairs of duplicated sync/load/reorder functions in `TimerView` (`syncBenchManager`/`syncActiveManager`, `reorderBench`/`reorderActive`, etc.). Collapsing them into one role-tagged type let `TimerView` replace those pairs with single functions parameterized by `role` and a `cachedManagers: [PlayerOrderRole: OrderManager]` dictionary instead of two parallel cached-instance optionals. A class hierarchy would bring that duplication back — `@Query` would need to fetch each subclass separately, so the two-cached-instance pattern returns — unless the shared logic were rewritten to accept a base-typed instance directly rather than dispatching on `role`. SwiftData class inheritance for `@Model` types is also newer (iOS 18+) with rougher edges around polymorphic `@Query` predicates, migrations, and sync — complexity this local-only app (ADR-0001) doesn't need for two types that behave identically today. The tradeoff: this makes Bench vs. Active a runtime distinction instead of a compile-time one — nothing stops a caller passing a `.bench`-scoped manager where `.active` is expected, caught only by the `role` check, not the type checker. If Bench and Active ever need genuinely different behavior, that's the signal to revisit and split them into subclasses with real overrides.
